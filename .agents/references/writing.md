# 記事執筆フェーズ

検証結果をもとに、ブログ記事の下書きを作成するフェーズ。

## フロー概要

```
Step 1: 状況確認と案内 — 検証結果・ブログポイントを要約し、執筆方針を確認する
Step 2: 下書き作成 — テンプレートに沿って記事を書き、ユーザーのフィードバックで仕上げる
Step 3: 下書きレビュー — 別コンテキスト（または複数モデル並列）による第三者レビュー（任意）
Step 4: 日本語推敲（yomiyasu） — 意味を保ったまま AI 調・読みにくさを整える（任意）
Step 5: フェーズ完了確認 — ユーザーの合意を得て draft_completed へ
```

## Step 1: 状況確認と案内

NOTES.md・poc/・project.yaml を確認し、以下のテンプレートでユーザーに案内する:

> 記事執筆フェーズです。検証結果を確認しました。
>
> **記事の概要:**
> - タイトル: （project.yaml から）
> - 読者ターゲット: （NOTES.md の企画から）
>
> **ブログポイント（NOTES.md より）:**
> - （ブログポイントを箇条書きで要約）
>
> この内容で記事の下書きを作成します。記事の構成や書き方について希望はありますか？なければ、テンプレートに沿って書き始めます。

## Step 2: 下書き作成

`blog/<article-id>/draft.md` にテンプレートに沿って記事を書く。

**モデル分担（[model-routing.md](model-routing.md) 参照）:**
- 対象ロール: `drafting`
- `inherit` の場合はメインエージェント自身が執筆する
- 別モデルが設定されている場合は、`blog/<article-id>/draft.md` の執筆・改稿を委譲し、完了後にメインエージェントが確認してユーザーへ提示する

テンプレート: [templates/draft.md](../templates/draft.md) （`.agents/templates/draft.md`）
テンプレートはユーザーが自由にカスタマイズしている可能性がある。テンプレートの構成に従うこと。
テンプレート内の HTML コメント（`<!-- ... -->`）にはユーザーからの指示が書かれている。各セクションに何を書くべきかの指針になるので、コメントの内容に従って執筆する。

下書きを作成したらユーザーに確認を依頼する。フィードバックがあれば修正し、合意が得られるまで繰り返す。

下書きが完成したら、レビューを提案する:

> 下書きが完成しました。
>
> 下書きの内容を別コンテキストでレビューさせることをお勧めします。記事の正確性や読みやすさを第三者目線でチェックできます。
> レビューしますか？

ユーザーがレビューを希望したら Step 3 へ。スキップする場合は Step 4 へ進む。

## Step 3: 下書きレビュー

別コンテキストのレビュー担当に下書きのレビューを依頼する。

**モデル分担（[model-routing.md](model-routing.md) 参照）:**
- 対象ロール: `draft_review`（未指定なら `review`）
- 権限: **完全読み取り専用**（ファイル編集禁止）
- `inherit` の場合も、必ず別コンテキストのサブエージェントを起動する
- 複数モデルが設定されている場合は並列起動し、重複整理・見解相違を含めて 1 つの表に統合する

レビュー担当には `blog/<article-id>/draft.md` と `NOTES.md` を渡し、以下の観点で評価させる:

- 検証結果と記事の内容に齟齬がないか
- 記事の構成は読みやすいか
- ブログポイントが漏れなく記事に反映されているか

### レビュー結果の提示

レビュー結果は**必ず表形式でユーザーに提示する**。エージェントが勝手に修正してはいけない。

単一モデルの場合:

| # | 指摘内容 | 修正方針 |
|---|---------|---------|
| 1 | （レビュー担当の指摘を要約） | （エージェントが考えた修正案） |
| 2 | ... | ... |

複数モデル並列レビューの場合（[model-routing.md](model-routing.md) 参照）:

| # | 指摘内容 | 指摘モデル | 修正方針 |
|---|---------|-----------|---------|
| 1 | （重複整理した指摘内容） | Model A, Model B | （エージェントが考えた修正案） |
| 2 | （見解相違があれば両論を併記） | Model A / Model C | （推奨方針と理由） |

提示後、以下のテンプレートで案内する:

> 下書きレビューの結果です。上記の修正方針で進めてよいでしょうか？
> 修正方針を変えたい項目や、対応不要と判断する項目があれば教えてください。

ユーザーの合意を得てから修正を実施する。修正が完了したら Step 4 の日本語推敲を提案する:

> 下書きレビューの修正が完了しました。
>
> 仕上げとして `yomiyasu` スキルで日本語を推敲することをお勧めします。意味と事実を保ったまま、不自然な比喩・曖昧な主述・AI 調の装飾を整えられます。
> 日本語推敲を実行しますか？

ユーザーが推敲を希望したら Step 4 へ。スキップする場合は Step 5 へ進む。

## Step 4: 日本語推敲（yomiyasu）

同梱の `yomiyasu` スキル（`.agents/skills/yomiyasu/SKILL.md`）を使い、`blog/<article-id>/draft.md` の日本語表現を推敲する。

**モデル分担（[model-routing.md](model-routing.md) 参照）:**
- 対象ロール: `polishing`
- `inherit` の場合はメインエージェント自身が `yomiyasu` スキルを実行する
- 別モデルが設定されている場合は、`.tmp/` への推敲済み出力と `yomiyasu_check.py run / verify` の実行までを委譲し、`draft.md` 本体への反映はユーザー合意後にメインエージェントが行う

### 実行条件とテンプレートとの整合

`yomiyasu` を実行する際は、以下の条件を明示する:

- **標準パラメータ**: `--doc-type article --stance=説明 --material NOTES.md`（`--reader` は `NOTES.md` の読者ターゲットから `expert` / `informed` / `general` を選定）
- **テンプレート構成の保持**: [templates/draft.md](../templates/draft.md) で指定された SEO 用の導入文、`## この記事の要約`、`## さいごに` の見出しと役割は「依頼で指定された構成」として残し、文章表現のみを整える
- **出力先**: 原文 `blog/<article-id>/draft.md` は直接書き換えず、一時ファイル（例: `.tmp/<article-id>-draft.yomiyasu.md`）へ出力し、`yomiyasu_check.py run` と `verify` を実行する
- **プロジェクト語彙**: リポジトリルートの `.yomiyasu-words/`（`allow.txt` / `flag.txt` / `flag-patterns.txt`）が自動適用される

### 推敲結果の提示と反映

推敲と検査が完了したら、エージェントが勝手に `draft.md` を上書きせず、以下の内容をユーザーに提示して確認を求める:

- **変えたところ**（主な変更点の要約）
- **残したAIっぽいところ**（該当がある場合）
- **書き手に確かめたい点**（該当がある場合）
- **確認の記録**（`yomiyasu_check.py` の検査結果）
- 推敲済み一時ファイルのパス（`.tmp/<article-id>-draft.yomiyasu.md`）

> `yomiyasu` による日本語推敲が完了しました。上記の内容で `blog/<article-id>/draft.md` に反映してよいでしょうか？
> 戻したい表現や、確認事項への回答があれば教えてください。

ユーザーの合意を得たら `blog/<article-id>/draft.md` に反映する。

**反映後の `textlint` チェック:**
`draft.md` へ反映した際に `textlint`（`preset-ja-technical-writing` / `@textlint-ja/preset-ai-writing`）の指摘が出た場合は、**意味と文の働きを変えない最小修正**で解消し、修正した箇所があればユーザーに報告する（安易な `textlint-disable` は避ける）。

## Step 5: フェーズ完了確認

まず機械チェックを実行する:

```bash
.agents/scripts/check-phase.sh <article-id> draft_completed
```

このスクリプトは project.yaml への記事登録、draft.md の存在、本文が参照する画像の存在、textlint の合格を検証する。NG が出た場合は解消してから再実行し、合格を確認する。

合格したら、以下のテンプレートで案内する:

> 記事執筆フェーズはこれで完了でよいでしょうか？
> よければ phase を `draft_completed` に更新します。次は WordPress への投稿に進むことができます。

ユーザーが合意したら `project.yaml` の `phase` を `draft_completed` に設定する。

## phase 遷移条件

`draft_completed` に遷移するには、以下がすべて満たされていること:

- `blog/<article-id>/draft.md` が作成されている
- `.agents/scripts/check-phase.sh <article-id> draft_completed` が合格している
- ユーザーが下書きの内容を確認し、合意している
- 下書きレビューが完了している（ユーザーがスキップした場合は不要）
- レビューを実施した場合、指摘事項について修正方針を合意し反映済みである
- `yomiyasu` による日本語推敲が完了している（ユーザーがスキップした場合は不要）
- 推敲を実施した場合、推敲結果を確認・合意して `draft.md` に反映済みであり、`textlint` を通過している
- ユーザーがフェーズ完了に合意している

## リファレンス

### 書き方のルール

#### コードブロック

- 言語指定を必ず付ける（```typescript, ```yaml 等）
- コードブロックの前に、何を見せるかを1文で説明する
- コードブロックの後に、ポイントや注意点を箇条書きで説明する
- 長すぎるコードは要点を抜粋し、全体はGitHubリポジトリへのリンクで補足する

#### 画像

- 画像は `blog/<article-id>/images/` に配置する
- Markdown内では相対パスで参照する: `![説明](images/xxx.png)`
- WordPress MCP が自動でアップロード・URL置換する
- 説明的なファイル名を付ける（連番は使わない。例: `grafana-dashboard-overview.png`）

**POC の画像を記事に使う場合:**

`poc/images/` から `blog/<article-id>/images/` にコピーする。NOTES.md の `-> ブログ:` マーカーが付いた画像を確認し、記事に必要なものを選ぶ。

**追加のスクリーンショットが必要な場合:**

記事を書いている途中で、POC にはない画像が必要になることがある（手順の途中画面、設定画面、エラー画面など）。その場合は `screenshot` スキルで撮影し、`blog/<article-id>/images/` に直接保存する。

#### リンク

- 公式ドキュメントや参考記事は積極的にリンクする
- GitHubリポジトリの URL は目立つように単独行で記載する

#### その他

- 実際に試した結果に基づいて書く（推測で書かない）
- ハマりポイントや注意点は明示する（NOTES.md の `-> ブログ:` マーカーを参考に）

### WordPress MCP で使えない記法

以下の Markdown 記法は WordPress MCP で正しく変換されないため、使わないこと:

- **コードブロックのファイル名指定**: ````typescript:app.ts` のような記法は効かない。ファイル名はコードブロックの直前にテキストで書く
- **タスクリスト**: `- [ ]` / `- [x]` は使わない。通常のリストで代替する
- **H1 はタイトル専用**: H1 は投稿タイトルに自動変換され本文から除去される。本文の見出しは H2 以下を使う
