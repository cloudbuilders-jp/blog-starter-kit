# マルチモデル分担ガイド（Model Routing）

このリポジトリでは、ワークフロー内の各工程を役割（ロール）単位で異なるモデルに分担できます。
設定はテンプレート共通の [models.yaml](../models.yaml) と、個人・環境別の `.agents/models.local.yaml` で管理します。

---

## 1. 設定ファイルの読み込みルール

エージェントはセッション開始時、またはタスクを委譲する前に以下の順で設定を読み込みます。

1. `.agents/models.yaml`（リポジトリ同梱のデフォルト設定）
2. `.agents/models.local.yaml`（存在する場合のみ読み込み、ロール単位で上書き）

### 解決の優先順位

- `roles.<role>` が `.agents/models.local.yaml` に定義されていればその値を使う
- 未定義または `null` の場合は `.agents/models.yaml` の値を使う
- レビュー個別ロール（`ideation_review` / `poc_review` / `draft_review`）が未定義または `null` の場合は `roles.review` にフォールバックする
- 最終的に未指定のロールは `inherit`（現在のセッションモデル）として扱う
- `on_unavailable` や `cli_runners` も同様に `.agents/models.local.yaml` の定義で上書きする

---

## 2. ロール定義と権限境界

**鉄則:** `NOTES.md` と `project.yaml` の更新は常に **メインエージェント（`main`）のみ** が行います。

| ロール | 担当内容 | 書き込み可能範囲 | `inherit` 時の実行方式 | 複数モデル指定 |
|---|---|---|---|---|
| `main` | 対話進行・意思決定確認・`NOTES.md` / `project.yaml` 更新・最終統合 | プロジェクト全体 | 現在のセッション自身 | 不可（単一） |
| `poc` | 検証調査・PoC コード実装・デバッグ | `poc/` 配下のファイル編集・検証コマンド実行まで可（`NOTES.md` / `project.yaml` は不可） | メイン自身が実行 | 不可（単一） |
| `drafting` | 記事下書きの作成・大幅な改稿 | `blog/<article-id>/draft.md` の作成・編集まで可（完了後にメインが確認・提示） | メイン自身が実行 | 不可（単一） |
| `polishing` | `yomiyasu` スキルによる日本語推敲 | `.tmp/` 配下への推敲結果出力と `yomiyasu_check.py run / verify` まで可（`draft.md` 本体への反映はユーザー合意後にメインが実施） | メイン自身が実行 | 不可（単一） |
| `review`（および `ideation_review` / `poc_review` / `draft_review`） | 企画・検証・下書きの第三者レビュー | **完全読み取り専用**（ファイル編集禁止。指摘と根拠のみ返却） | バイアス排除のため **`inherit` でも別コンテキストのサブエージェントを起動** | **可（並列パネル実行）** |

### `main` ロールの扱い

`main` に `inherit` 以外の推奨モデルが設定されていて、現在のセッションで起動しているモデルと異なる場合は、セッション開始時に 1 行だけ通知して作業を続行します（作業はブロックしません）。

> 通知例: `※ models 設定の main 推奨モデルは <モデル名> ですが、現在のモデルでそのまま続行します。`

## 3. エントリの記法

各ロールの値は以下のいずれかで記述できます。

```yaml
# 1. 親モデルを継承
drafting: inherit

# 2. モデル名のみ（文字列）
drafting: claude-opus-5-5

# 3. 詳細指定（オブジェクト）
polishing:
  provider: claudeAgent          # 任意: プロバイダー識別子（T3 Code 等で使用）
  model: claude-opus-5-5         # 必須: モデル名（または inherit）
  options:                       # 任意: モデル固有の推論強度・オプション
    effort: high                 # 例: effort / reasoningEffort / thought_level
  runner: native                 # 任意: native（既定）| cli

# 4. 並列レビュー用の配列（review 系ロールのみ）
review:
  - provider: claudeAgent
    model: claude-opus-5-5
    options:
      effort: high
  - provider: codex
    model: gpt-6.2-sol
    options:
      reasoningEffort: high
```

## 4. ランタイム別の委譲方法（ハイブリッド抽象化）

ロールに委譲対象モデルが設定されている場合、現在の実行環境に応じて以下の順で委譲手段を選択します。

### 優先 1: ネイティブ / オーケストレーター委譲（`runner: native`、既定）

| 実行環境 | 委譲方法 |
|---|---|
| **T3 Code** | 初回に `orchestrator_capabilities` で利用可能なプロバイダー・モデルを確認し、`delegate_task` で `providerInstanceId`・`model`・`options` を指定して委譲する |
| **Cursor / Antigravity 等** | 環境が提供するサブエージェント委譲ツール（`Task` / `invoke_subagent` 等）にモデルを指定して委譲する |
| **Claude Code** | 同一プロバイダー（Claude 系モデルや `opus` / `sonnet` / `haiku`、`inherit`）は `Agent` ツールの `model` パラメータで委譲する |

### 優先 2: オプトイン外部 CLI ランナー（`runner: cli` 明示時のみ）

ネイティブ委譲で呼べない他プロバイダーモデルをローカル CLI から呼びたい場合、設定で `runner: cli` と `cli_runner: <名前>` を**明示的に指定した場合のみ**使用できます。

**安全ルール:**
- 外部 CLI ランナーは **読み取り専用タスク（`review` 系、および標準出力で推敲案を受け取る用途）に限定**する。`poc` や `drafting` のようなファイル編集・コマンド実行を伴うロールでは使用しない。
- `cli_runners.<name>.command` のコマンドテンプレートに従い、標準入力または引数で自己完結プロンプトを渡して結果を受け取る。
- 実行前に該当 CLI バイナリの存在を確認し、未導入・未認証であれば後述の `on_unavailable` ルールに従う。

### 指定モデルが利用不可だったときの挙動（`on_unavailable`）

指定されたモデルやプロバイダー・CLI が現在の環境で利用できない場合、**設定を無視して黙って別モデルへ切り替えてはいけません**。`on_unavailable` の設定に従います。

- `ask`（既定）: 利用不可だったモデルと理由をユーザーに伝え、「親モデル（`inherit`）で続行する / 該当モデルのみスキップする / 設定を見直す」かを確認する。
- `fallback_inherit`: 親モデルで自動続行し、結果報告時に「指定モデル X が利用不可のため親モデルで実行した」旨を明記する。
- `error`: 処理を中断し、設定ファイル（`.agents/models.local.yaml`）や環境の確認を案内する。

## 5. 委譲プロンプト作成の基本ルール

委譲先（サブエージェント・別モデル・外部 CLI）は親スレッドの会話履歴を持っていない前提で、以下を必ず含めます。

1. **対象ファイルと前提資料**: 読むべきファイルパス（`NOTES.md`、`blog/<article-id>/draft.md` 等）と背景条件を自己完結で明記する
2. **役割と権限境界**: 編集してよいファイル範囲、または「読み取り専用（ファイル編集禁止）」であることを明記する
3. **評価観点・完了条件**: 何を確認・作成すれば完了かを箇条書きで明確にする
4. **根拠の明示**: レビュー時は確認できた事実と推測を分け、対象箇所（見出し・行番号・引用）を添えさせる
5. **モデル固有のプロンプト最適化**: 環境にクロスモデル最適化ガイド（例: `cross-model-prompting` スキル等）がある場合は、渡す先モデルに合わせて文言と `options` を調整する

---

## 6. 並列レビュー結果の統合ルール

`review` 系ロールに複数モデルが設定されている場合、メインエージェントは以下を行います。

1. **並列起動**: 設定された各モデルを独立した別コンテキストで並列に起動し、互いの出力を見せずにレビューさせる
2. **重複整理と統合**: 同じ論点の指摘は 1 行にまとめ、「指摘モデル」列に該当する全モデル名を並べる
3. **見解相違の明示**: モデル間で評価や推奨案が割れた論点があれば、隠さずに「見解相違」として両論を並記し、メインエージェントの推奨方針を添える
4. **単一の表で提示**: エージェントが勝手に修正せず、必ず以下の表形式でユーザーに合意を得る

```markdown
| # | 指摘内容 | 指摘モデル | 修正方針 |
|---|---------|-----------|---------|
| 1 | （要約した指摘内容） | Model A, Model B | （メインエージェントが考えた修正案） |
| 2 | （見解相違がある場合は両論を併記） | Model A（賛成） / Model C（反対） | （推奨案と判断理由） |
```

※ 単一モデルでレビューした場合は、従来の 3 列（`# | 指摘内容 | 修正方針`）またはモデル名を付記した 4 列のどちらでも構いません。
